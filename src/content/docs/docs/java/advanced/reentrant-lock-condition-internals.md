# ReentrantLock 与 Condition：状态变化与队列流转

本文聚焦 `ReentrantLock` 和 `Condition` 的运行过程，重点跟踪重入计数、锁释放与等待节点在队列间的转移。

常用场景、API 选择、公平性策略和基本使用规范已整理在 [Java 并发包（JUC）技术文档](/docs/java/basics/collections-concurrency/) 中。本文作为补充，避免重复介绍这些基础内容。

## 1. ReentrantLock 的状态模型

`ReentrantLock` 基于 AQS 的独占模式实现。理解其核心状态时，可以关注以下三项：

| 状态 | 含义 |
| --- | --- |
| `state` | 当前持锁线程的重入次数；`0` 表示锁未被持有 |
| 独占持有线程 | 当前获得锁的线程 |
| AQS 同步队列 | 获取锁失败、等待重新竞争的线程节点 |

`state` 是锁状态，不是等待线程数量。对于 `ReentrantLock`，成功重入会增加该值，匹配的 `unlock()` 会减少该值。

## 2. 重入与完全释放

假设线程 T1 连续获取同一把锁两次：

```java
lock.lock(); // state: 0 -> 1，T1 成为持有者
lock.lock(); // state: 1 -> 2，T1 重入
```

每次 `unlock()` 只减少一次重入计数：

| 操作 | `state` | 锁是否可被其他线程获取 |
| --- | ---: | --- |
| T1 第一次 `lock()` | 1 | 否，T1 持有锁 |
| T1 第二次 `lock()` | 2 | 否，T1 仍持有锁 |
| T1 第一次 `unlock()` | 1 | 否，T1 仍持有锁 |
| T1 第二次 `unlock()` | 0 | 是，锁完全释放 |

因此，加锁和解锁必须成对匹配。若持有次数为 2，只调用一次 `unlock()` 后，锁仍由当前线程持有；若当前线程并未持有锁却调用 `unlock()`，会抛出 `IllegalMonitorStateException`。

可重入使一个已持锁的方法能够调用另一个也需要同一把锁的方法，而不会等待自己释放锁。它只适用于同一线程、同一把锁，不会允许不同线程并发进入受保护区域。

## 3. Condition 与两类队列

每个 `Condition` 都与创建它的锁关联。理解 `await()` 和 `signal()` 时，要区分条件队列与 AQS 同步队列：

| 队列 | 保存的线程 | 进入条件 |
| --- | --- | --- |
| Condition 条件队列 | 等待业务条件成立的线程 | 持锁线程调用 `await()` |
| AQS 同步队列 | 等待获取锁的线程 | 获取锁失败，或已被 signal 转移等待重新获取锁 |

调用 `await()` 的线程不是普通地“排队等锁”：它先进入条件队列，并完全释放关联锁。收到通知后，它才转移到 AQS 同步队列，重新竞争锁。

## 4. `await()`：释放锁并等待条件

调用 `await()` 前，线程必须持有关联的 `ReentrantLock`。例如，T1 已经重入两次：

```java
lock.lock();
lock.lock();
try {
    condition.await();
} finally {
    lock.unlock();
    lock.unlock();
}
```

调用 `await()` 时，关键状态变化如下：

1. T1 的等待节点加入该 `Condition` 的条件队列。
2. 保存 T1 当前的重入次数，本例为 2。
3. 完全释放 T1 持有的锁，`state` 从 2 变为 0，使其他线程能够进入临界区。
4. T1 挂起，等待通知、中断或其他规定的返回条件。

`await()` 会完全释放锁，而不是只释放一次。否则，若 T1 仍持有一层重入锁，其他线程就无法获得锁来修改条件并发出通知。

## 5. `signal()`：通知并转移等待节点

调用 `signal()` 的线程必须先持有与该 `Condition` 关联的锁：

```java
lock.lock();
try {
    // 修改受 lock 保护的条件状态
    condition.signal();
} finally {
    lock.unlock();
}
```

`signal()` 的作用是从条件队列中选择等待节点，并将其转移到 AQS 同步队列。它不会释放调用线程持有的锁，也不会把锁直接交给被通知线程。

| 时点 | 被通知线程的状态 | 当前锁的持有者 |
| --- | --- | --- |
| `signal()` 前 | 位于 Condition 条件队列 | 通知线程 |
| `signal()` 后、通知线程解锁前 | 已转入 AQS 同步队列，等待获取锁 | 通知线程 |
| 通知线程解锁后 | 参与锁竞争 | 可能仍是其他竞争线程 |
| 被通知线程获取锁后 | `await()` 返回并继续执行 | 被通知线程 |

`signalAll()` 会把条件队列中所有等待节点转移到同步队列；这些线程随后仍需逐一竞争同一把锁。通知不代表条件一定仍成立，也不代表线程立即运行。

## 6. `await()` 返回与重入状态恢复

被通知线程先进入 AQS 同步队列，成功重新获取锁后，`await()` 才返回。锁的重入状态会恢复到调用 `await()` 前保存的值：

| 阶段 | T1 的锁状态 |
| --- | --- |
| 调用 `await()` 前 | `state = 2`，T1 持有锁两次 |
| `await()` 释放锁 | `state = 0`，T1 进入条件队列 |
| 收到 `signal()` | T1 节点转入同步队列，尚未持有锁 |
| T1 重新获取锁成功 | 恢复为 `state = 2` |
| `await()` 返回 | T1 在原临界区继续执行 |

要区分“收到通知”“进入同步队列”和“重新获得锁”这三个阶段，它们并不是同一件事。

## 7. 条件检查必须使用 `while`

```java
lock.lock();
try {
    while (!ready) {
        condition.await();
    }

    // 条件成立后执行
} finally {
    lock.unlock();
}
```

线程从 `await()` 返回后，应重新检查共享条件。原因包括虚假唤醒、多个等待线程竞争同一条件，以及通知后条件状态可能再次变化。使用 `if` 只检查一次，可能在条件仍不满足时继续执行。注意：线程被唤醒后，是从condition.await() 返回，继续往下执行，如果是 if（!ready）方法，线程并不会继续执行 if 判断。 

条件状态的读写应由同一把关联锁保护：等待方在锁内检查条件，条件不成立时调用 `await()`；通知方在锁内更新状态，再调用 `signal()` 或 `signalAll()`。

## 8. 完整队列流转

| 步骤 | 操作 | 节点所在位置 | 锁状态 |
| --- | --- | --- | --- |
| 1 | T1 持锁，发现条件不成立并调用 `await()` | Condition 条件队列 | T1 完全释放锁 |
| 2 | T2 获取同一把锁，更新条件并调用 `signal()` | T1 从条件队列转入 AQS 同步队列 | T2 仍持有锁 |
| 3 | T2 调用 `unlock()` | T1 在同步队列中竞争 | 锁释放 |
| 4 | T1 重新获取锁 | T1 离开同步队列 | 恢复调用 `await()` 前的重入次数 |
| 5 | `await()` 返回，T1 再次检查条件 | T1 执行业务代码 | T1 持有锁 |

## 9. 要点

- `state` 对 `ReentrantLock` 表示重入次数；只有降到 0 才完全释放锁。
- `await()` 保存重入状态、完全释放锁，并将线程放入条件队列。
- `signal()` 转移等待节点，不释放锁，也不直接唤醒线程继续执行。
- 被通知线程必须重新获取锁，`await()` 才会返回。
- `await()` 返回后必须重新检查条件，通常使用 `while`。
- Condition 条件队列与 AQS 同步队列用途不同，节点会在通知后从前者转入后者。
