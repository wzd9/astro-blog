之前的[服务器搭建](/blog/home-server-setup/)文章以 FRP 作为家庭服务器与公网服务器之间的主要通道：阿里云 Nginx 接收请求，再通过 FRPS/FRPC 转发到家中的 PVE 和 Ubuntu 虚拟机。这个方案能够快速解决没有公网 IP 的问题，但随着服务变多，继续为 PVE、数据库或其他管理服务增加映射端口，会扩大公网暴露面。

这次调整的重点不是“彻底移除 FRP”，而是给两类访问分工：**需要给普通访客使用的服务走公网入口；只有自己和受信任设备需要访问的管理服务走 WireGuard VPN。** 家庭网络与阿里云通过 WireGuard 组成一个受控网络，FRP 则只保留给 GitHub Actions 自动部署使用的通道。

## 新版架构

![WireGuard 家庭服务器架构图](/images/blog/wireguard-home-server/architecture.png)

图中的 IP 地址和端口均为示例，请以自己的实际网络规划、安全组和服务配置为准。

新版架构可以分为四个区域：

| 区域 | 核心组件 | 职责 |
| --- | --- | --- |
| 公网入口 | 域名、阿里云 Nginx | 接收网站等明确需要公网访问的 HTTP/HTTPS 请求 |
| VPN 网关 | 阿里云 WireGuard Server、家庭侧 WireGuard Peer | 为云服务器、PVE 和受信任客户端建立加密的私有访问路径 |
| 家庭内网 | N150 主机、Proxmox VE、Ubuntu 虚拟机 | 承载业务应用、数据库、缓存、博客和音乐服务 |
| 运维与部署 | Uptime Kuma、Bark、GitHub Actions、FRP | 可用性监控、告警和自动部署 |

## 为什么要从“端口映射”转向“组网”

FRP 很适合把某个明确的内网服务暴露给公网，但它不是内网管理的最佳入口。每新增一个映射服务，都需要重新考虑端口、访问控制、认证、扫描风险和后续维护。

例如 PVE 管理界面、MySQL、Redis 等服务本来就不应直接面向公网。即使额外配置了密码、HTTPS 或 IP 白名单，暴露入口本身仍增加了攻击面。

WireGuard 的工作方式不同：客户端先使用密钥建立 VPN，再通过私有网段访问目标服务。对 PVE 来说，电脑或手机接入 VPN 后，就像位于被允许的内网路径中，而不是先访问一个公开的 PVE 端口。

```text
旧方式：公网客户端 → FRP 映射端口 → 家庭内网服务

新方式：受信任客户端 → WireGuard 加密隧道 → 阿里云 → 家庭内网 → PVE / Ubuntu 服务
```

这并不意味着 WireGuard 能替代所有公网入口。博客、公开 API 或其他面向访客的服务仍需要经过域名、Nginx 和 HTTPS 对外提供；WireGuard 解决的是**管理面与私有服务的访问边界**。

## 网络与角色规划

以下地址仅为示例，避免与家庭路由器已有网段冲突是第一原则。

| 节点 | 示例地址 | 角色 |
| --- | --- | --- |
| 阿里云轻量应用服务器 | 公网 IP | Nginx、WireGuard Server、监控和部署入口 |
| WireGuard Server | `21.98.0.1/24` | VPN 网关，负责客户端与家庭网段的路由 |
| 手机 | `21.98.0.9/32` | WireGuard 客户端，用于移动网络下的安全管理 |
| 电脑 | `21.98.0.10/32` | WireGuard 客户端，用于日常维护与排障 |
| 家庭 LAN / PVE | `21.98.0.0/24` | 家庭服务器网段；PVE 是主要管理目标 |
| Ubuntu 虚拟机 | `21.98.0.20` | 运行应用、MySQL、Redis、博客和 Navidrome 等服务 |

WireGuard 使用独立的 VPN 网段，例如 `21.98.0.0/24`；每个客户端在 Peer 配置中只分配自己的 `/32` 地址。服务端还需要知道到达家庭网段的路由，家庭侧 Peer 则应允许回程访问 VPN 网段。具体 `AllowedIPs`、转发和防火墙规则要与实际网卡、PVE 网桥和局域网地址保持一致。

## 三条关键访问链路

### 1. 访客访问公开服务

公开网站不需要也不应该要求每位访客安装 VPN。请求仍走标准的公网入口：

```text
Internet
  → 域名解析
  → 阿里云 Nginx（80 / 443）
  → 已明确配置的后端服务
```

Nginx 负责 TLS 终止、反向代理和站点路由。只有确实需要公开提供的服务才应出现在这条链路上；PVE、MySQL、Redis 等管理或数据服务不在其中。

### 2. 自己管理 PVE 与家庭服务

电脑或手机先连接 WireGuard，再访问 PVE 或 Ubuntu 的私网地址：

```text
电脑 / 手机
  → WireGuard（UDP 51820）
  → 阿里云 WireGuard Server
  → 家庭侧 WireGuard Peer
  → PVE / Ubuntu 虚拟机
```

这样 PVE 的 Web 管理端口只需要对家庭网络和 VPN 路径可达，无需创建公网 FRP 映射。访问数据库、Redis 或仅供内部使用的应用时，同样优先使用私网地址，并继续保留服务自身的认证与最小权限配置。

### 3. GitHub Actions 自动部署

自动部署仍保留一个窄化的 FRP 通道：

```text
GitHub Actions
  → SSH 到阿里云部署入口
  → FRP 部署通道（仅 remotePort 9000）
  → 家庭服务器部署脚本
```

这里的 `9000` 指**部署用途保留的 FRP 代理端口**，不再用来映射 PVE、数据库或日常业务服务。FRPC 与 FRPS 建立连接所使用的控制端口应按实际配置和安全组规则单独管理；它不是给公网用户访问业务服务的入口。

部署账户应使用专用 SSH 密钥，限制可执行命令和可写目录；部署包校验、服务重启和失败回滚也应在脚本中显式处理。这样即使自动化链路出现问题，影响范围也被限制在部署流程内。

## 端口暴露策略

“减少端口暴露”不是指把所有端口关闭，而是只保留必要的、职责明确的入口。可以按下表进行梳理：

| 类型 | 端口示例 | 是否应公网开放 | 说明 |
| --- | ---: | --- | --- |
| HTTP / HTTPS | `80`、`443` | 是 | 网站等公开服务的标准入口，由 Nginx 管理 |
| WireGuard | UDP `51820` | 是 | 仅用于 VPN 握手和加密流量，不直接暴露 PVE 或数据库 |
| SSH | `22` | 按需 | 建议限制来源 IP、使用密钥登录并关闭密码登录 |
| FRP 部署代理 | `9000` | 按需 | 只用于 GitHub Actions 自动部署，不再承载日常服务映射 |
| FRPS 控制端口 | 按实际配置 | 仅家庭侧需要 | 仅允许 FRPC 建立控制连接；不要误认为它是业务公网入口 |
| PVE / MySQL / Redis | 如 `8006`、`3306`、`6379` | 否 | 仅允许家庭 LAN 和 WireGuard 路径访问 |

安全组与云服务器防火墙需要同时维护：云安全组只放行必要端口，操作系统防火墙再按来源网段细化规则。WireGuard Peer 只为可信设备创建，不共享私钥；设备遗失或不再使用时，应立即移除对应 Peer。

## WireGuard 配置与验证要点

WireGuard 的配置很短，但网络连通依赖多个环节。部署时可按以下顺序检查：

1. 为云服务器、家庭侧节点、电脑和手机分别生成独立密钥对；私钥只保留在对应设备上。
2. 在阿里云安全组和系统防火墙中允许 WireGuard 的 UDP 端口，例如 `51820/udp`。
3. 在云服务器开启 IPv4 转发，并为 VPN 网段与家庭网段配置正确的路由和防火墙放行规则。
4. 在家庭侧 Peer 中声明家庭网段，在云端 Peer 中声明到家庭网段的可达路由；确认回程流量不会被路由器或防火墙丢弃。
5. 使用手机 4G/5G 和电脑外部网络分别测试握手、访问 PVE、访问 Ubuntu 私网服务和 DNS 解析。

常见问题通常不在 WireGuard 的密钥本身，而在以下位置：`AllowedIPs` 写错、未开启 IP 转发、缺少回程路由、PVE/Ubuntu 防火墙未放行 VPN 网段，或把 TCP 规则误用于 WireGuard 的 UDP 端口。

## 监控与日常维护

阿里云上的 Uptime Kuma 继续负责可用性检查，Bark 负责向 iPhone 推送告警。监控项应同时覆盖公网入口和私网链路：

- 域名与 HTTPS 证书是否可用；
- 阿里云 Nginx、WireGuard 接口和家庭侧 Peer 是否正常握手；
- PVE 与 Ubuntu 虚拟机是否可达；
- 博客、业务应用、MySQL、Redis、Navidrome 等关键服务是否健康；
- GitHub Actions 部署任务和 FRP 部署通道是否可用。

监控本身也要遵循权限边界：能通过 VPN 检查的私网服务不要再为了监控而新开公网端口。对失败告警，应区分“公网入口异常”“VPN 不通”“家庭主机离线”和“单个应用故障”，这样排障更快。

## 小结

这次升级后，阿里云仍然是公网入口和 VPN 网关，PVE 与 Ubuntu 仍然负责家庭侧的计算与服务承载；变化在于访问方式：

- **公开服务**继续走域名、Nginx 与 HTTPS；
- **PVE 和私有服务**通过 WireGuard 进入家庭网络，不再依赖公网端口映射；
- **FRP**只保留自动部署所需的单一代理端口 `9000`；
- **监控、告警与最小权限**贯穿公网与内网两侧。

从“把服务一个个映射出去”转向“先建立可信网络，再访问私有服务”，可以显著缩小家庭服务器的公网暴露面，也让后续增加管理服务时更容易保持边界清晰。
